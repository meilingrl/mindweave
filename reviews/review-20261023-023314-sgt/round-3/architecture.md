# 第三轮独立架构／数据审查：v3 时序推演

日期：2026-10-23。完整阅读了 v3 两文档与第二轮汇总，未阅读其他本轮报告。本轮全部是纸面事件推演，没有运行原型、测试、构建、数据库或真实模型，也没有读取应用用户数据。仅写本报告，未改冻结副本或原件。

## 结论与推演口径

要求的五条时序在 v3 推荐规则下均已能够推出安全结果；MW-02 的候选只读／编辑基线、MW-04／06 的退出失败返回工作区、MW-12 的自动标题保护，解决了第二轮对应反例。但新增一个 MW-06 的组合反例：**持久化分支来源成功，不代表它所依赖的最新源正文也已经持久化**。在退出保存失败后返回工作区的情境中，这会造成已保存来源指向仅存在过于内存的文字。

下表中的“唯一”指用户可观察的安全结果与不变量明确，不指线程调度、精确 SQL、压缩算法或模型返回文字已经唯一。所有推演均假定采用本副本推荐规则；涉及产品取舍仍待用户批准。不能据此宣称方案已实现或经过故障注入。

## 1. MW-03／04：两名额占满→第三排队→改配置→停止→迟到块／旧检查点

依据：[架构 v3 §11.R、§12.R](../v3/architecture-discussion.md)第 201、224–229 行；[需求 v3 §7](../v3/initial-requirements.md)第 170 行。

| 事件 | 事件后状态 | 不变量／是否唯一 |
| --- | --- | --- |
| 接受不同会话的 R1、R2，均使用连接 P | 用户消息与任务先提交；R1、R2 占满两名额 | 本地接受记录在外部请求之前；唯一 |
| 接受第三个会话的 R3 | R3 的目的地 P、模型参数、输入范围冻结；本地提交后排队；无第三个执行名额 | 两名额上限与排队身份明确；唯一 |
| 用户将活动配置改为 Q | 后来的新操作可选 Q；R1、R2、R3 的既有快照仍为 P | 不重新读取活动配置改写旧任务；唯一 |
| 停止 R1，保留当时已接受文字 T1 | R1 成为取消终态；可分支时正文不再增长。退出入口尚未封闭，因此空闲名额可领取 R3 | R3 仍向 P 执行，不抢占 R2；唯一的配置／范围，具体领取时刻可异步 |
| R1 的迟到分块 D 到达 | D 不能追加到 T1，也不能更新 R3；R1 身份已终结 | 旧任务不影响终态或别的任务；唯一 |
| R1 的旧检查点 T0 比终态保存更晚到写入入口 | T0 不得回退较新内容或取消状态；内存仍为 T1 | 单调提交原则明确；唯一。此处不虚称终态已经落盘 |
| R3 执行中用户停止 R3 | 保留其已接收部分，标取消；没有隐式改用 Q 重发 | 停止与快照边界明确；唯一 |

**结果：** 既有迟到事件、旧保存和配置漂移反例闭合。实际能否满足它需要以后验证任务身份与写入顺序；纸面没有证明当前原型或正式实现能做到。

## 2. MW-04／06：退出→保存失败→返回→新提问→再次退出→重启

依据：架构第 229 行、需求第 172 行。为区分可恢复内容，下表用 M1/M2/M3 表示内存接受状态，D0 表示失败前最后成功提交的数据库状态。

| 事件 | 事件后状态 | 不变量／是否唯一 |
| --- | --- | --- |
| R1、R2 运行，R3 排队；用户确认退出 | 新操作和新队列启动入口关闭 | 取消释放的名额不能给 R3；唯一 |
| 收束任务 | R1、R2 停止并保留部分文字；R3 为未执行取消；内存为 M1 | 运行与未执行状态可区分；唯一 |
| 最终保存失败 | M1 与错误保留，窗口不静默消失；磁盘仍仅保证 D0 及已成功提交部分 | 不把失败说成已保存；唯一 |
| 用户选择“返回工作区” | 新操作／调度入口重开；R1、R2、R3 保持终态；旧队列不重建 | 恢复工作台不等于恢复旧任务；唯一 |
| 用户提出新问题 R4，但本地提交仍失败 | 保留输入，R4 不进入外部执行 | 即使工作区可操作，未提交请求不能发送；唯一 |
| 存储恢复后再次显式提交 R4，提交成功 | 新任务身份及问题已落盘，R4 可以入队／执行；内存变 M2；旧任务不复活 | 只有新的被接受操作可执行；唯一 |
| 用户再次选择退出，R4 此时仍运行 | 再次封闭入口，停止 R4；内存 M3 包含新问题、新部分回答和新的取消状态 | 不复用 M1 的旧退出快照；唯一 |
| 最终保存 M3 成功后关闭 | 正常退出的最终提交包含最新接受状态 | “重试退出”保存当前状态；唯一 |
| 重启 | 读取已提交内容；所有已取消任务不运行；若仍有非终态记录，只标中断，不自动重发 | 重启不恢复执行。最后页面／后退栈范围仍依推荐待用户批准 |

**结果：** 第二轮“窗口还在却无法继续”和“恢复工作区复活队列”的反例已被明确排除。这里的新发送先提交规则不能自动证明分支／总结的来源依赖也已提交；后者是本轮 MW-06 新反例。

## 3. MW-05：A→B→C 冻结后继续 A／B→组装 C

依据：需求第 104 行；架构第 211、226 行。

| 事件 | 事件后状态 | 不变量／是否唯一 |
| --- | --- | --- |
| A 已有终态回答 a2，从其选区创建 B | B 的直接来源是 a2，背景边界为 A 截至 a2 | 记录来源操作，不猜测；唯一 |
| B 已有终态回答 b2，从其选区创建 C | C 继承 B 已冻结的 A≤a2，再增加 B≤b2 的范围 | 多层祖先冻结明确；唯一 |
| A 继续产生 a3、a4 | A 当前记录增长；B、C 已冻结的 A 边界不变 | C 不沿 A 当前末尾读取；唯一 |
| B 继续产生 b3、b4 | B 当前记录增长；C 的 B 边界不变 | C 不纳入后来 B 消息；唯一 |
| C 接受问题 c1，等待执行期间 A／B 又增长 | C 请求固定自身当时输入范围；祖先边界仍为 A≤a2、B≤b2 | 不因排队扩大祖先或自身输入范围；唯一 |
| 组装 C 上下文 | 可用来源域只含冻结祖先范围、选区／来源与接受时 C 自身消息；不含 a3/a4、b3/b4 或兄弟分支 | 排除边界唯一；预算与压缩后的精确提示文本留实施设计，不伪称已确定 |
| C 返回来源，再从 B 返回来源 | 依直接来源依次定位 b2、a2，不靠访问栈是否保留 | 来源与普通后退独立；唯一 |

**结果：** 没有发现必须复制全部祖先或引入第二份来源事实库的理由。终态文字在内存不再增长，并不单独证明其已持久化，持久依赖仍按新增 MW-06 检查。

## 5. MW-02：候选只读、采用、编辑基线改变

依据：需求第 124–126 行；架构第 280–282 行及第 201 行。

| 事件 | 事件后状态 | 不变量／是否唯一 |
| --- | --- | --- |
| 当前采用 V1，生成候选 C1（基线 V1） | 当前仍 V1，C1 待处理；节点不重复 | 后台完成不切换当前正文；唯一 |

| 用户先手改 V1 并保存为 V2，然后尝试采用 C1 | C1 基线 V1 与当前 V2 不同，采用前说明替换且历史可回看；拒绝则当前保持 V2 | 采用动作绑定 C1；唯一的安全分支 |
| 用户确认采用 C1 | 当前成为 C1，待处理候选位置释放，V1／V2 历史保留，已读不重置 | 指针与版本操作原子；唯一 |

| E 的保存动作到达 | 不无提示覆盖 C2；保留 E 并提示基线已变，等待处理 | 唯一的安全结果；后续处理 UI 未指定不构成静默覆盖 |
| 对照：当前仍 C1，E 正常提交为新当前 V3 | 旧版本保留；V3 沿用 C1 来源／覆盖范围，手改不把后来消息标成已总结 | 版本身份、生成基底和覆盖范围分开；唯一 |

**结果：** 编辑入口与采用入口的保护现在一致。不要求在本轮加入候选直接编辑、版本恢复、自动合并或复杂差异界面。

## 本轮新高价值反例

### MW-06（新增子例）：已保存来源引用可能依赖未提交的终态源正文

- **文件章节：** [架构 v3 §11](../v3/architecture-discussion.md)第 174–175 行、§11.R 第 196–203 行、§12.R 第 228–229 行；[需求 v3 §5.2／§5.3](../v3/initial-requirements.md)第 96–113 行及 §7 第 172 行。现有明确原子边界是“分支＋来源记录”，未明确包含被引用正文的最新持久版本。
- **触发反例与事件后状态：**

  | 事件 | 内存 | 已提交数据 |
  | --- | --- | --- |
  | 回答收到“蒸汽机改变了运输”，尚未保存最新分块 | 完整接受文字含“运输” | 源消息仅有早先前缀“蒸汽机改变了” |
  | 确认退出并停止回答，最终保存失败 | 源消息取消终态，末尾文字仍在；新任务入口暂关闭 | 最新正文与终态未提交，旧前缀仍是可恢复内容 |
  | 返回工作区；存储随后恢复；用户从“运输”创建分支 | 按现规则，终态可分支；新分支来源校验在内存通过 | 若仅提交分支＋来源，则新分支已保存，但源正文仍是旧前缀 |
  | 在下一次源正文检查点前强制终止并重启 | 内存新正文消失 | 已保存分支的引用范围／hash 无法在保存的源文中成立 |

- **影响：** 正确拒绝来源定位可以避免跳错，但无法兑现“已保存分支及准确来源可恢复”的承诺；这与仅丢失最后未保存分块不同，因为系统已经持久保存了依赖该分块的来源记录。来源关系不应通过猜补正文修复。
- **依据可信度：** **合理风险**。尚无正式存储实现，不声称已经发生坏数据；统一写入、禁止旧快照回退和内存终态稳定都没有单独排除此提交顺序。
- **优先级：** **开发前明确不变量**；实施中验证真实事务与失败路径。
- **最小修订：** 创建持久来源引用时，所依赖的消息正文、终态及冻结边界必须已经提交，或与该引用同一事务提交；失败则不能留下对外表示已保存的来源关系。适用于分支及同类总结来源，不要求复制全部祖先，不要求每个 token 同步落盘，也不要求扩大备份／修复功能。
- **需否用户决定：** **无需新增产品决定**。它是既有准确来源与保存恢复承诺的必要细化；整体退出恢复和单写者限制仍待用户批准。
- **最低成本验证及通过标准：** 本轮先以表中事件检查事务依赖。以后使用独立临时库：让最后源正文保存失败，再令分支创建写入成功，立即终止后重开。通过标准只有两类合法结果：① 源正文／终态／冻结边界和新来源均已提交，返回来源校验通过；② 依赖提交失败，分支不被声明保存成功且不存在持久悬空来源。不得以静默改引用或搜索相同文字代替。

## 收敛判断

本轮不是零新问题轮：上面的 MW-06 子例需要补充来源持久依赖约束后再次核对。除此之外，指定的五条时序没有发现新的高价值反例。单写者、总结接受时机／候选限制、历史范围与整体恢复仍只属于提案；平台、Markdown、数据库与课程运行证据保持原有未验证状态。
