# 第一轮独立架构／数据审查

审查日期：2026-10-23。审查对象为本次 `v1` 副本，不是正式实现。未阅读其他审查报告，未运行构建、测试或原型，未读取应用用户数据，未修改原始需求、架构、README、代码或数据。本报告只依据文档内部契约和已声明的原型证据；没有新增外部能力判断。

## 结论

四工程、纯 Avalonia、Application 协调生成、SQLite 保存事实、从事实推导总结网络、来源与阅读位置分开，这些方向可以共同成立，当前没有发现必须推翻路线的已证实矛盾。主要缺口在异步任务、存储提交和导航恢复相交的几个边界：单条原则分别成立，不足以确定两个事件竞争时谁生效。

以下 A-01～A-07 是会影响外部行为的契约缺口，A-08 是正式依赖选定后的验证项。它们均不表示原型已有对应缺陷，也不表示用户已经批准建议。第 18 节的恢复提议仍待确认；本轮审查不能把它升级为批准。

## 高价值问题

### A-01 排队任务何时冻结配置与内容范围，尚无一个可解释的时点

- **定位：** [架构 §12](../v1/architecture-discussion.md)第 190–199 行、§13 第 205、214 行；[需求 §7](../v1/initial-requirements.md)第 152、155 行。当前只明确“运行中的请求”使用不可变配置，队列中的请求如何受后续修改影响未定义。
- **触发反例：** 两个请求占满名额；用户在会话 C 发送问题，任务进入队列。随后将活动连接从服务 P 改为服务 Q，继续在父会话新增消息，再切换工作区。C 开始执行时，是发送按下发送时的内容到 P，还是把后来上下文发到 Q？用户只确认过一套活动配置，不能从现有文字判断此次发送的实际目的地和范围。排队总结也存在同样的范围时点问题。
- **影响：** 同一次发送的目的地、模型身份与来源范围不稳定；“用户知道哪些内容交给 AI”和“分支背景冻结”难以验收。优先级只需定义队列选择顺序，无须因此增加抢占或后台系统。
- **依据可信度：** **合理风险**；已证实的是文档未覆盖排队阶段，不是已证实发送错误。
- **优先级：** **开发前明确**。
- **最小修订：** 统一“接受请求／排队／开始执行”的含义，并明确哪个时点冻结配置身份、模型参数和输入范围。建议接受用户操作时冻结；若选择执行时冻结，必须让排队期间修改会影响该任务这一行为可见。区分冻结引用范围与复制整份历史，不要求冗余保存所有文本。
- **需否用户决定：** **需要**，这是修改设置是否影响已排队任务的可观察语义；实现快照方式无需用户决定。
- **最低成本验证与通过标准：** 先对上述 P→Q、父消息新增的事件列一张预期表。通过标准是每个排队任务都能唯一指出连接／模型和消息范围，设置修改不能造成表外变化；后续用两个占位请求的可控队列验证即可，无须真实付费调用。

### A-02 “停止后可分支／退出后保存”需要共同的终态边界

- **定位：** 架构 §3 第 51–57 行、§11 第 172–173 行、§12 第 194–199 行；需求 §5.2 第 92 行、§7 第 151–153 行。
- **触发反例：** 用户停止一个回答，界面已允许从其文字创建分支；此时网络仍交付一个已在途分块，或较旧的定期保存尚未执行。若迟到分块继续追加，刚建立的来源不再对应已停止正文；若旧快照最后写入，可把已停止状态写回生成中或截短正文。退出时还有排队请求：取消一个运行任务释放名额，调度器恰好启动下一个任务，退出保存的范围再次变化。
- **影响：** 来源稳定、取消保留部分内容、不自动续写与退出保存可能互相破坏。取消网络调用成功与本地业务终态已提交不是同一个事件。
- **依据可信度：** **合理风险**；文档给出了正确目标，但没有给出竞争发生时的提交规则，不能据此指称现有实现有竞态。
- **优先级：** **开发前明确**，具体调度与同步手段在实施中验证。
- **最小修订：** 增加一个行为不变量：回答一旦对外成为可分支的终态，该次生成不能再改写其正文或终态；旧保存不得覆盖更新状态。确认退出后停止接收新操作、停止调度排队任务，收束现有任务，再保存其最终本地状态；排队任务也属于退出处理范围。保存失败是否恢复可操作窗口，仍按 §18 待确认，不在此默认批准。
- **需否用户决定：** 终态不可再增长和队列不在退出中启动属于既有承诺的必要细化，**无需额外产品决定**；保存失败后的整体退出规则仍需用户确认。
- **最低成本验证与通过标准：** 先排演“停止→建分支→迟到分块”“旧保存→取消终态→旧保存落盘”“退出→名额释放→队列待启动”。通过标准：终态正文不再改变、来源仍验证通过、重启无自动执行，退出期间没有新请求获得执行名额。以后可用可控流和延迟存储实现验证，不需要真实服务。

### A-03 冻结的是消息编号范围，还是当时的正文版本，必须说清

- **定位：** 架构 §12 第 190–192 行、§15 第 236–238 行；需求 §4.2 第 75 行、§5.2 第 95 行、§5.4 第 111–115 行。原消息改写虽被排除，正在生成的消息仍会增长。
- **触发反例：** 用户在父会话 A 的回答 a3 仍输出时，主动总结“当前会话”；总结记录了“截至 a3”，但 a3 在总结真正读取或排队执行前又多了数段。再次打开总结时，仅凭截止消息 ID 无法证明当时覆盖的实际文字。另一个路径是 A→B→C：若 C 的来源只记 B 的截止点，而重建祖先上下文时沿 A 的当前末尾读取，就会混入 B 创建以后 A 新增的内容。
- **影响：** “固定生成范围”“后续内容未纳入”与冻结祖先背景不能由同一份数据可靠解释；重试同一任务可能基于不同输入。此问题不要求为每个分支复制全部祖先历史。
- **依据可信度：** **合理风险**；多层范围的递归冻结可以从现有原则推出，但尚无明确持久化契约；生成中消息的冻结条件确未写明。
- **优先级：** **开发前明确**。
- **最小修订：** 对分支背景声明：继承各级已冻结来源边界，不追溯祖先当前末尾。对总结声明：冻结范围必须能唯一还原当时实际纳入的正文；若范围中有增长消息，选择“截至最后一条终态消息”或“明确保存当时部分正文／长度与校验”，并将部分回答状态保留给总结。不得只用一个可变消息的 ID 表示已冻结内容。
- **需否用户决定：** **需要决定生成中总结的行为**；祖先冻结的递归性是现有承诺的细化，无需重选上下文架构。
- **最低成本验证与通过标准：** 用 A→B→C 和 a3 增长的固定文字列出每个任务应看到的字符串。创建后继续增长 A、B，重新组装 C，结果必须不包含后来祖先内容；总结的覆盖范围必须能与一份确定文字核对，“后续内容”提示也必须能区分已纳入与未纳入部分。

### A-04 总结版本规则缺少并发提交时的唯一结果

- **定位：** 架构 §15 第 228–238 行、§11 第 173 行；需求 §5.4 第 113–115 行、§7 第 151–152 行。每会话最多一个“回答”不必然约束该会话的总结任务。
- **触发反例：** 尚无总结节点时双击总结，两个任务先后成功，都认为自己是首次生成；或者再次生成期间用户保存手写版本，新结果稍后完成；再或者用户打开候选 X 后，另一个候选 Y 完成，用户原来的“采用”操作误用最新候选。单个 SQLite 数据库和统一写入协调不会自动定义这些产品结果。
- **影响：** 一个会话出现重复节点、当前版本跳回旧状态、手写修改被替换，或采用的版本不是用户实际读到的版本，直接违反既有稳定节点与独立已读规则。
- **依据可信度：** **合理风险**；未发现现有文字直接矛盾，但竞争时没有唯一合法转移。
- **优先级：** **开发前明确**。
- **最小修订：** 最小方案可限制每会话一个总结生成任务，重复操作复用／拒绝已有任务；节点归属会话唯一。生成完成、手动保存、采用与丢弃均针对明确版本身份，节点当前指针与版本记录以原子操作改变。生成期间已有当前版本发生变化时，新生成结果仍作为候选，不能凭旧基线覆盖；首次成功竞争也不能产生第二节点。无需复杂差异比较或分布式版本系统。
- **需否用户决定：** “不覆盖手写内容、采用明确版本”无需重审；**若要允许同时生成多个候选，才需要用户明确交互**。为首版采取单个总结任务是建议，尚未获批准。
- **最低成本验证与通过标准：** 排演双击首次生成、生成中手动保存、打开 X 后 Y 完成三例。通过标准：每会话只有一个稳定节点；所有已保存手写版本仍可读；采用动作总是采用其指定版本；候选的已读状态不因采用改变。后续用可控完成顺序验证数据库事务与用例即可。

### A-05 正式存储仍缺少“哪些状态可以安全降级”的恢复底线

- **定位：** 架构 §11 第 170–176 行、§18 第 273–282 行；需求 §5.1 第 85 行、§5.3 第 107 行、§7 第 154 行。原型 README 已有损坏原文件保护，不能自动等同正式 SQLite 已选策略。
- **触发反例：** 应用接受新问题并发送给服务，但对应用户消息与占位回答尚未持久化就崩溃；或数据库升级失败后启动流程将数据库当作“空工作区”继续写。另一种较轻故障是已保存当前页面指向不存在的内容；若把这类 UI 引用失效与核心消息损坏采用同一回退方式，会扩大本可局部降级的问题。
- **影响：** 外部请求已发生却没有可恢复的本地记录；恢复可能覆盖唯一历史；一条陈旧视图状态可能阻止本来可读的消息和总结。把草稿归为 UI 状态也不能据此降低“保存后仍恢复”的既有承诺。
- **依据可信度：** **合理风险**；数据库迁移／恢复在 §11、§18 明确待细化，因此这是开发边界缺口，不是漏实现的指责。
- **优先级：** **开发前明确恢复底线**；迁移实现和真实故障注入在实施中验证。
- **最小修订：** 明确权威事实为消息及其状态、来源、总结节点／版本；图边为派生数据，布局／视口／最近页面可独立降级重建。用户草稿须保留其已确认的持久化承诺。接受发送时先持久保存用户输入与请求对应记录，再执行外部请求；重启仅标中断，不据此保证外部服务恰好执行一次。打开／迁移失败不得新建空库覆盖原库；页面／视口失效允许回到安全入口，事实关联失效则明确诊断，不猜补关系。具体后退栈恢复仍待用户确认。
- **需否用户决定：** 无损保护和不自动重发是既有原则，**无需新增功能决定**；整体恢复、迁移失败后可用模式仍需在正式方案中确认。数据库备份／修复产品不由本项自动授权。
- **最低成本验证与通过标准：** 先制定四个预期：发送后进程中断、迁移中断、最后页面失效、来源关联损坏。通过标准：原资产不被替换为新空库；已保存事实保留；仅 UI 引用失效不阻断可读内容；恢复不产生新 API 请求、不伪造来源。后续使用独立临时数据库验证，不接触用户数据库。

### A-06 多实例策略不能晚于共享数据库与全局调度的实现

- **定位：** 架构 §11 第 176 行、§12 第 195 行、§15 的当前版本规则。两个原型均明示没有多实例协调，此证据不支持正式版多写者安全。
- **触发反例：** 用户连续启动两个进程访问同一个本地数据库；两个 Application 协调器各运行两个请求，合计四个；两个窗口分别编辑同一个总结当前版本，后写者覆盖前者的指针或编辑基线。SQLite 即使成功串行写入，也不能替产品决定四个请求是否违规、两个采用操作谁可生效。
- **影响：** 全局两个请求与总结版本保护的实际范围不确定；单数据库事务不足以消除陈旧业务决策。问题不要求首版支持多窗口协作。
- **依据可信度：** **合理风险**；多实例尚待细化是已声明事实，没有证据证明正式方案已经保证安全。
- **优先级：** **开发前明确**。
- **最小修订：** 选定最小策略并写明作用范围。首版可只允许一个数据库拥有写入实例，第二次启动转到已有实例或明确拒绝；若选多写者，必须另外定义共享调度与冲突处理，不能只引用 SQLite 锁。锁遗留／进程异常后要有可判定的再次打开路径。
- **需否用户决定：** **需要确认是否接受单个写入实例这一首版限制**；不应由审查默认增加多窗口能力。
- **最低成本验证与通过标准：** 两个进程同时启动访问独立临时库，再终止首个进程并重开。通过标准由所选策略决定；若单写者，则任意时刻只有一个进程能执行写用例或调度请求，异常退出后可重新取得使用权，不删除原库、不冒用仍存活的实例。

### A-07 三层导航的职责合理，但 Content 历史与工作区范围还未确定唯一权威

- **定位：** 架构 §4 第 67–75 行、§11 第 178–186 行、§18 第 277–280 行；需求 §5.3 第 102–107 行、§6 第 145 行。
- **触发反例：** 在工作区 A 从网络打开总结，再回来源会话；随后切到工作区 B，按普通后退。如果使用全局 Content 历史，可能回到 A；若每工作区各有历史，则应回到 B 的最近详情。若 Menu 同时保留自己的详情缓存、Content 再有一份历史，还可能出现菜单仍选网络、正文却显示另一工作区会话的组合。“工作区不是额外一层导航”没有决定历史归属。
- **影响：** 后退、返回来源和切换工作区虽已分出意图，整体状态仍可能由多个所有者分别更新，造成可见范围与详情错配；也使“只恢复最后页面、不恢复完整栈”的待定问题被实现默认决定。
- **依据可信度：** **合理风险**；不是指控现有设计已有两套栈，也不要求套用其他项目的具体类名。
- **优先级：** **开发前明确用户语义**，服务与 ViewModel 的具体形态实施中确定。
- **最小修订：** 指定一份 Content 访问历史的唯一权威，以及它是全局还是按工作区／主区分隔；导航意图解析后，应一致更新目标工作区、主区和内容。返回来源仍按来源边解析，不能用普通弹栈冒充。暂不选择持久化历史；§18 仍标待定。
- **需否用户决定：** **需要决定跨工作区／主区按后退的行为及重启历史范围**；内部只维护一份权威状态不需要用户挑选类或框架。
- **最低成本验证与通过标准：** 用两工作区和网络→总结→会话的事件表列明每步工作区、Menu、Content 和 Back 目标。通过标准：每一步只有一个预期，三者始终对应同一可解释的作用范围；“返回来源”不依赖刚好存在某条访问历史。无须先写导航框架。

### A-08 来源适配的持久数据必须与未来渲染变化区分版本

- **定位：** 架构 §14 第 218–224 行、§11 第 170、176 行；[LiveMarkdown 小样 README](../../../prototypes/livemarkdown-chat/README.md)“锚点实际含义”与“边界”。正式依赖版本尚未选定。
- **触发反例：** 正文原文完全没改，但正式版更换 Markdown 渲染版本或配置，使某来源块的拆分、序号或 `LayoutText` 变化。旧的显示锚点被原校验拒绝是安全行为，却不能据此声称旧存档仍具有同等定位能力；盲目重新解释旧 UTF-16 偏移则可能跳到另一个重复词。
- **影响：** 旧数据的来源关系可能仍在，但可定位程度下降；数据库迁移成功不能等同来源适配迁移成功。已有同一版本的小样证据不能覆盖版本升级。
- **依据可信度：** **待验证假设**；未比较不同版本，也没有声称某个固定版本已经不兼容。
- **优先级：** **实施中验证**；无需现在重新选择渲染器。
- **最小修订：** 来源持久结构具备可识别的锚点格式／解析配置身份，原文消息及引用仍是独立事实。遇到未知格式或不兼容布局，保留原数据并明确无法准确定位，不能直接用新布局解释旧显示偏移。正式锁版时列入来源兼容性检查，不扩大为通用 Markdown 字符映射需求。
- **需否用户决定：** 安全拒绝已在需求内，**无需新产品决定**；若未来要改为近似定位或承诺升级后全部自动迁移，再由用户决定。
- **最低成本验证与通过标准：** 当前阶段只需静态确认拟定存档能区分格式／配置；以后仅在准备变更渲染版本或配置时，用重复词、跨格式跨段的旧固定样本回放。通过标准：要么定位原选区并通过校验，要么明确拒绝且保留引用与原文；不得跳到相似文字。

## 保留的架构结论

1. **四工程依赖可成立。** Core 不依赖 UI／数据库／供应商 SDK；Application 依赖 Core 并声明所需副作用契约；Infrastructure 实现它们；Desktop 作为组合入口接入基础设施，ViewModel 经用例工作。启动组装依赖 Infrastructure 不等于 ViewModel 必须依赖它。没有证据需要新增第五工程或通用仓储框架。
2. **三层导航与工作区作用范围可以共存。** 工作区不必成为第四层；Root、Menu、Content 已有不同职责。A-07 要求明确历史所有权和边界，不要求推翻三层结构，也不冒称已经满足课程全部验收。
3. **事实与派生图的选择一致。** 首版来源边来自真实会话路径，总结节点来自保存总结；只保存布局／视口并不需要第二份图数据库。未来语义关联已明确排除，不应以未来能力反推现在必须存图。
4. **来源与阅读位置分离正确。** 来源是探索关系，阅读位置是可更新的恢复偏好；普通切换和返回来源不能共享一个模糊的“滚动位置”。富文本显示锚点加校验符合当前能力边界，不是缺乏精确原文映射就整条路线不可行。
5. **模型扩展边界基本完整。** 连接、模型配置、协议适配器、选择策略分开且不暴露 SDK 类型，足以支持首版单配置及以后增加协议。无需现在实现动态插件、多提供商 UI 或自动兜底。A-01 只补排队阶段的快照语义。
6. **稳定总结节点与版本独立状态合理。** 候选、当前版本和版本已读各有职责；网络不应把每个版本复制为新节点。A-04 聚焦并发提交，不要求重做版本产品设计。

## 驳回或降级的疑点

- **“SQLite 会自动保证应用级任务／版本一致性”——驳回。** 它是存储选择，不能替代 A-02、A-04、A-06 的业务条件；反过来也不能以存在这些条件认定 SQLite 选错。
- **“LiveMarkdown 必须提供通用原文逐字符映射才可采用”——驳回。** 当前已明确区块＋显示锚点及拒绝不确定定位，未承诺该能力。复杂 Unicode、表格等仍是明确未验证项，不应改写成已通过或必然失败。
- **“SDK／组件版本已经由原型锁定”——驳回。** 架构 §5.2、§14 明说正式版本待确认。没有核对或声称最新版本的能力，本轮不借最新行为反推旧版。
- **“任务在后台持续就是关闭窗口后台常驻”——驳回。** 文档描述的是切换页面后生成持续与确认退出时停止，两者并不矛盾。
- **“§18 已经批准只恢复最后页面”——驳回。** 该节明确待用户确认；本轮 A-05、A-07 均保留其待定身份。
- **“草稿属于 UI 状态即可丢弃”——驳回。** 草稿持久化早已在需求中确认；状态分类不撤销保存与恢复承诺。
- **“必须立刻确定布局算法、精确 token 公式、SQL 表／索引、导航类名、重试库、缓存策略”——降级。** 这些可以在实施设计或验证时确定；当前只需解决会改变用户可观察结果的契约边界。本轮未以抽象可扩展性为由要求新增功能。
