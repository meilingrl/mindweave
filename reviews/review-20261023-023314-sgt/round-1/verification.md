# 第一轮独立实现、验证与课程审查

审查对象为 `v1/initial-requirements.md` 与 `v1/architecture-discussion.md`，另独立读取项目 README、两个原型 README、LiveMarkdown 小样的项目文件、锚点与相关测试源码。只读核对课程 DOCX 和官方固定版资料；未阅读其他审查者报告，未运行、编译或测试任何原型，未访问用户应用数据。本报告没有给出新的运行通过结论。

结论：现有方案足以继续设计讨论，证据措辞总体审慎；以下三项值得在正式实施方案形成前补清。它们是验收契约缺口，不证明已确认技术路线不可行，也不授权增加产品范围。当前仍不能据此判定课程验收、正式实现或使用价值通过。

## 成立并应保留的结论

1. **两套原型与正式产品分离成立。** 架构 §9、§14 和两个 README 已分别说明：Avalonia 11 聊天原型的用户实机确认、Avalonia 12 组件小样的有限技术记录、尚未建立正式实现。31/31 与 8/8 是既有记录，本轮未重跑，不能改称本轮独立复现通过。
2. **固定依赖描述可由独立资料支持。** 小样项目文件第 2–7 行确为 net10.0、Avalonia 12.1.4、LiveMarkdown 2.5.1。官方 NuGet 2.5.1 nuspec 对应 commit `fbb6bc1d52980d725d3bedff4f72b762ebd1149b`，依赖 Avalonia ≥12.0.0、Markdig ≥1.1.2；与 12.1.4 的版本关系合理。包声明兼容与 macOS 运行记录不能推出 Windows 文本交互已经通过。[官方固定包](https://api.nuget.org/v3-flatcontainer/livemarkdown.avalonia/2.5.1/livemarkdown.avalonia.2.5.1.nupkg)、[Avalonia.Desktop 12.1.4](https://www.nuget.org/packages/Avalonia.Desktop/12.1.4)。
3. **锚点能力边界表述正确。** 架构 §14 没有把显示偏移冒充精确 Markdown 原文偏移。小样 `SelectionAnchor.cs:29–51,54–76` 实际采用正文前缀校验、源块范围、同范围序号、布局文本校验及局部选区；仅源块与显示文字相同时设置精确原文起点，并在恢复时重验。原消息首版禁止改写，进一步降低了跨编辑恢复的范围。
4. **“后台全量解析、视觉增量更新”描述成立。** 固定 commit 的 `MarkdownUpdateProducer.cs:178–192,225–238` 对捕获的完整快照调用 Markdig，再发布 Full/Incremental 更新；不是增量解析器。小样 `StreamingAndFileTests.cs:16–45` 的旧块/选区/视口断言有针对性；它覆盖一个选定旧块和固定追加片段，不是通用性能证明。
5. **四工程没有被课程原件直接否定。** 课程 P9 明确要求反映思想、无需采用相同技术；单向核心/UI 分离可由四工程表达。不能仅因 ViewModel 放在 Desktop 就判定违规，或强迫复制 Worklog/DailyPoetryA 的目录与类名。需要补的是下述可审查职责。

## V-01 三层导航尚缺课程要求的状态归属与统一目标契约

- **位置：** 架构 §4（第 65–73 行）、§11（第 178–186 行）。
- **反例：** 实施者可以写三个名称正确的服务，但让各服务私自维护内容历史，或由 View/code-behind 另存当前详情与返回栈；也可以把目标字符串散落到命令中。这仍可能满足当前文字中的“服务契约访问”“由 ViewModel 维护相关状态”，却不满足课程 P20 对统一目标常量、`MainViewModel.ContentStack / PushContent / GoBack` 及接口/状态边界的具体要求。当前 Root“初始化/恢复到主工作台的切换”也未说明与课程所述窗口/根生命周期如何对应。
- **影响：** 产品功能可用后仍可能因课程要求返工导航；多个历史权威还会混淆普通后退与返回来源。这里不判定已经违规，因为正式代码尚未实现。
- **依据与可信度：** 高。课程原件 P19–20 的明确文字；另只读核对本地 DailyPoetryA 的 `MainViewModel.cs:54–65,87–99`、`IContentNavigationService.cs:3–12`、`ContentNavigationService.cs:8–23`。原件与定位方法见 [课程证据](verification-evidence-course.json)。
- **优先级：** 开发前明确。
- **最小修订：** 在 §4 或 §11 补一段验收契约：三层服务分别管理根/窗口生命周期、主区切换、内容推栈；目标由统一标识契约定义；主 ViewModel 是业务内容栈唯一权威，导航服务不持有第二套栈；统一参数入口与 ViewLocator 真正参与渲染。允许等价设计，无需强制方法名逐字相同。Root 若采用单窗口初始化状态，写明等效生命周期与可演示行为，不能仅凭层名认定合规。
- **是否需要用户决定：** 延续已确认三层要求不需重问。若主动偏离课程 P20 的窗口切换或栈归属，才需要老师/用户确认其等价性；本审查不替老师批准。
- **最低成本验证与通过标准：** 设计阶段静态列出 Root→主工作台、Menu→主区、Content→两级详情→后退三条路径，标出唯一状态所有者和统一目标/参数入口。实施后检查没有服务/视图私有业务栈，并观察实际 ViewLocator 输出及后退行为；本轮不执行这些运行检查。

## V-02 首版范围尚未与课程工作量及交付硬门槛建立对照

- **位置：** 架构 §4 末段（第 75 行）；需求 §8（第 158–196 行）与 §9。
- **反例：** 一个聊天 View 展示很多会话并不自动算很多页面；业务复杂、工程多、测试多也不能证明页面和类/接口数量达到参照要求。只完成聊天与网络的功能场景，仍可能遗漏指定 PDF 报告，或在打包时把两个原型的 artifacts/bin/obj 带入 ≤10MB 的源码资源包。
- **影响：** 当前无法判断选定首版是否覆盖课程工作量，也无法从功能通过推到提交合格；临近提交才建立口径可能迫使增加无意义页面或拆分类。
- **依据与可信度：** 高。课程原件 P5–7 明确实际意义、页面基准、接口/类 70% 和源码资源包 ≤10MB、不含编译结果；P29–31 与 P34–53 规定报告模板与 PDF。现有 §4 虽诚实承认还有数量/报告/包体要求，但没有落到项目对照。见 [课程证据](verification-evidence-course.json)。
- **优先级：** 开发前明确工作量基准；交付文件的实际检查在实施中完成。
- **最小修订：** 增加一个小型课程对照表，登记本地参照路径/版本、计数口径、Mindweave 对应的有意义页面与模型/接口职责、验证时机；另记源码资源包 ≤10MB、排除编译结果、PDF 报告及模板章节。只映射现有范围，先不增加功能。本地 `course/daily-poetry-a` 可作为待核准参照候选，但不能把未经确认的静态计数当成老师基准。
- **是否需要用户决定：** 不需要为了补对照重选产品。老师原文未说明“接口和类”合计还是分别计数、壳/设计/测试类及窗口是否算页面；若这一口径影响达标判断，需要老师确认。不得自行选择最有利口径后宣称通过。
- **最低成本验证与通过标准：** 先固定参照目录与版本及排除项，手工审查有意义页面和类/接口映射；实施后按同口径统计。提交前检查压缩包内容与大小、报告格式及模板章节齐全。通过标准是可复核地达到原件门槛，不能以“预计够多”或原型测试数替代。本轮未建立老师认可的数值基准，未给出数量达标结论。

## V-03 首版 Markdown 的可分支支持面与降级行为尚未定义

- **位置：** 需求 §5.2、§8.1、§9；架构 §14（第 218–224 行）。
- **反例：** 真实模型输出表格、公式、图片或带嵌入控件的行内结构时，渲染成功不代表选中内容能作为完整引用用于分支。固定版 API 的 `LayoutText` 在嵌入控件处使用 U+FFFC，子文字块有独立坐标；小样直接取各块 `LayoutText[start..end]` 作为 Quote（`SelectionAnchor.cs:39–48`）。若照搬这种 Quote 到上下文组装，尚未验证的结构可能得到占位字符、缺失文字或不确定的拼接顺序。此反例是未验证路径，不声称当前示例已发生错误。
- **影响：** 正式版可能做到“渲染了回答”却无法稳定完成核心的“选文字→带上正确引用→分支→返回”；目前需求没有规定遇到这些结构时应允许、拒绝还是降级，因此不能形成明确验收样本。
- **依据与可信度：** API 事实高，具体失败概率未知。固定 commit 的 [MarkdownTextBlock.cs 第 115–117、164–181 行](https://github.com/DearVa/LiveMarkdown.Avalonia/blob/fbb6bc1d52980d725d3bedff4f72b762ebd1149b/src/LiveMarkdown.Avalonia/Controls/MarkdownTextBlock.cs#L164) 区分 `ActualText` 与 `LayoutText`；[固定版 README 第 303–331 行](https://github.com/DearVa/LiveMarkdown.Avalonia/blob/fbb6bc1d52980d725d3bedff4f72b762ebd1149b/README.md#L303) 说明源版本和坐标，公式还需额外包/节点注册（第 333–347 行）。现有文档已明确这些内容未验证，没有过度声称；缺的是面向首版的处理契约。独立取证元数据见 [库证据](verification-evidence-library.json)。
- **优先级：** 开发前明确支持与降级规则；实施中验证代表样本。
- **最小修订：** 明确首版“可阅读渲染”“可复制引用”“可创建来源分支”各自支持哪些文本结构，并规定未支持结构不提供误导的创建入口，或明确拒绝并保留可阅读原文。无需现在要求公式/图片/全部 Unicode 达标，也不应把旧原型的子集永久定为能力上限。将最小必验集覆盖普通段落、重复词、粗体/链接/行内代码、跨段、列表/代码等首版实际承诺结构；对不支持者记录明确降级。
- **是否需要用户决定：** 需要用户确认首版支持面是否足以满足其探索场景，尤其表格/公式是否为门槛。具体适配 API 与测试实现由开发负责，不需逐项让用户拍板。
- **最低成本验证与通过标准：** 先写少量真实形态的固定 Markdown 样本，逐一列出所见文字、送入 AI 的引用和返回目标；在正式实现阶段验证。通过标准是所有承诺结构的引用不含非预期占位/漏字、源定位正确，保存重启仍可恢复；未承诺结构有清楚拒绝/降级。原文精确偏移仅在确有映射时输出。本轮未运行样本，不能写成已通过。

- “两个原型版本不同证明选型冲突”：驳回。它们明确隔离，旧原型只保留交互依据；正式依赖尚未锁定，后续再复核。
- “必须把四工程改成两工程才能课程合规”：驳回。原件允许等效技术和分层，不能把示例目录当作唯一合法设计。
- “状态恢复 §18 未回答就已默认同意”：驳回。当前文件清楚标为待用户确认；本审查不替用户决定是否持久化完整后退栈。
