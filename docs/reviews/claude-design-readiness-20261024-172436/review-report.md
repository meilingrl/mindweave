# Mindweave 详细设计就绪审查报告

**审查日期：** 2026-10-24 · **审查者：** Claude（独立工程审查）
**对象：** [v1 需求](v1/initial-requirements.md)（v0.10）与 [v1 架构](v1/architecture-discussion.md)（2026-10-24 现行稿），基线见 [baseline.md](baseline.md)
**结论：** **可以有条件进入详细设计**，条件与依据见 §5。

本报告不是开发授权，也不证明产品可靠或有价值。问题编号 `MW-Cxx` 为本次新编，与既有复审的 [MW-01…MW-12](../review-20261023-023314-sgt/ISSUES.md) 区分；已由 D1–D8 确认、或旧清单已处理的事项不重复提出。

## 1. 审查方法与边界

- 依次阅读个人 AGENTS 规则、项目 README、需求、架构、设计沿革，按需查阅 D1–D8 讨论记录、既有问题清单与四个原型 README。
- 以 D1–D8 和现行文档为准；历史“待定”不覆盖后续决定。原型通过只作为其 README 所述场景的证据。
- 每个问题都用具体操作序列或失败场景说明，未凭抽象原则提出。
- 只读：未运行构建、测试、原型或付费 API，未读取密钥。

## 2. 总体判断

现行两份文档的产品边界、四工程职责、D1–D8 口径、版本与布局保存规则**基本一致**，已经覆盖多数易出错的并发场景（终态屏障、冻结范围、迟到命名、保存失败保留内存）。没有发现需要推翻已确认方向的问题，也没有发现会导致大面积返工的架构错误。

剩下的风险集中在三类“文档各处都对、但拼起来缺一块”的地方：

1. **数据引用关系没有汇总**：删除检查依赖“其他来源引用”，但没有一处列出谁会引用谁；上下文摘要可被兄弟分支复用，却没有说明归属（MW-C02）。
2. **运行期状态的归属没有汇总**：未保存布局、视口、后退历史和生成中正文分别出现在网络、导航、生成三个章节，各自正确，但没有说清它们活在哪个对象里；若按页面实例去实现，会悄悄丢失未保存布局（MW-C03）。
3. **“终态固定”与“重试”之间缺规则**：文档要求终态后正文不变、可以从停止的回答创建分支，又要求支持重试，但没说重试保存成什么（MW-C01）。

这三项如果留给各模块详细设计分别处理，持久化、生成和网络三份设计会各自做出不兼容的假设，因此列为 A 类；它们都能从已确认决定推导出唯一合理的数据规则，已在 v2 补全，只有交互入口的取舍列为待用户决定。

## 3. 问题清单

格式：位置 · 场景 · 影响 · 处理 · 解决阶段 · 是否需用户决定。位置中的“需求”“架构”指 v1 对应章节。

### A 类：进入详细设计前必须澄清（已在 v2 依据现有决定补全）

#### MW-C01 回答重试与“终态正文固定”、来源锚点之间没有保存规则

- **位置：** 需求 §6.2、§9.1（“重新生成应有明确状态”）、§9.5；架构 §4.1（终态后正文固定）、§14.1（重试交互未获确认）。
- **场景：** 回答 A1 生成到 40% 被停止 → 用户从 A1 选一句话创建分支 B（允许从已停止回答分支）→ 回到父会话点“重试”。
  - 若实现为覆盖 A1：B 的锚点哈希校验失败，返回来源被拒绝；B 的冻结范围指向的正文已不是创建时的内容。
  - 若实现为追加 A2 但没有取代关系：下一轮续聊把半截 A1 和完整 A2 一起发送，模型看到重复且矛盾的回答；总结覆盖范围也不知道哪一条有效。
- **影响：** 来源失效或上下文污染；Message 表结构、上下文组装、总结覆盖三份设计会各自猜。
- **为何不能留给详细设计：** 它决定 Message 的结构（是否有尝试关系）和上下文组装的选择规则，是持久化与生成两模块的共同输入。
- **处理（v2 已补全）：** 依据“终态后正文固定”“来源保护”推导：用户消息和已结束回答不可改写；重试另存为新回答并记录取代关系，旧尝试保留可读；续聊默认取每个提问的最新尝试。需求 §6.2、架构 §4.1。
- **需用户决定：** **U1**：是否对*已完成*回答也提供“重新生成”入口（不阻断，保存规则相同）。

#### MW-C02 引用清单缺失，上下文摘要的归属不明，删除检查无法完整实现

- **位置：** 需求 §8.2（“无其他来源引用……检查冻结范围等依赖”）、§9.6（“复用未失效摘要”）；架构 §4.1 实体表（缺上下文摘要、编辑草稿、布局、显示名、连接配置等）、§6.2（摘要表结构留待实施）、§9.1。
- **场景：** 子会话 C1 续聊时把祖先 A 的第 1–20 条消息压缩为摘要 S；兄弟分支 C2 随后复用 S（文档允许复用）。用户删除 C1（无总结、无子分支、无任务，符合删除条件）。
  - 若 S 按“发起请求的会话”归属并随 C1 级联删除：C2 下一次续聊的输入记录指向已删除的 S，重建失败或静默改用其他材料。
  - 若因 C2 在用而不删 S：S 的归属变得不确定，以后谁来清理、何时失效都无从判断。
- **影响：** 悬空引用或无主数据；删除检查只能“看侧栏子节点”，正是文档明确禁止的做法。
- **为何不能留给详细设计：** 引用清单是建表、外键、删除事务和清理策略的共同前提；持久化模块是最先开始的详细设计，没有清单就无法定稿。
- **处理（v2 已补全）：** 补全逻辑实体（ContextSummary、SummaryEditDraft、NodeLayout、显示名字段、连接配置、归档标记），新增“引用清单与删除检查”表，并写明不变量：**跨会话引用只指向祖先链；上下文摘要归属被覆盖消息所在的会话**。由此“无子分支”即保证没有其他会话引用本会话。架构 §4.1、§4.2。
- **需用户决定：** 否（是已确认删除规则的实现前提）。

#### MW-C03 运行期状态的唯一持有者没有汇总

- **位置：** 需求 §7.3–7.4、§9.3；架构 §3.4（主 ViewModel 保管历史）、§6（生成不属于 View）、§11.1（NetworkViewModel 管理待保存状态）、§11.3（视口“不依赖控件实例一直存活”）。
- **场景 1（布局）：** 用户在网络里点“整理布局”（产生待保存）→ 切到“探索”主区读一会儿 → 回到“网络”。若待保存布局放在 NetworkViewModel 实例里、而该实例随 Menu 切换重建，整理结果静默消失；按规则只有切换工作区或退出才会提示，所以用户没有任何机会保存。
- **场景 2（生成）：** 会话 X 正在生成，用户关闭会话页去看总结，再回到 X。若会话页从数据库读取，而数据库只有落后几秒的检查点，用户会看到正文“倒退”，随后再跳回最新。
- **影响：** 违反“保存失败或未保存时保留内存布局”的已确认规则；界面状态与真实状态不一致。
- **为何不能留给详细设计：** 这些状态跨导航、网络、生成三个模块，分别设计时每个模块都会默认“别的模块持有”。
- **处理（v2 已补全）：** 新增架构 §2.2“运行期状态归属”表：生成中正文与队列归生成协调器；每个工作区的历史、内存布局、修订号、视口、选择归主 ViewModel 下的工作区运行期状态；View 只持有几何与动效。同时写明四工程依赖方向。
- **需用户决定：** 否。

#### MW-C04 “第一版优先通过回到来源继续”含义不清，影响来源记录结构

- **位置：** 需求 §6.5 第二段。
- **场景：** 详细设计者把“优先”理解为“也支持从总结正文选区直接分支”，于是把 BranchSource 设计成“来源可以是消息或总结版本”的多态结构；总结版本可删除、正文可被手改，来源保护、删除检查和锚点适配都要多处理一类对象。
- **影响：** 首版数据模型和删除规则膨胀，且与 §5.2 首版清单不一致。
- **为何不能留给详细设计：** 它决定 BranchSource 的结构和删除检查范围，属于持久化模型输入。
- **处理（v2 已补全）：** 依据 §5.2 首版清单（“打开总结、回到来源继续聊”），明确首版不从总结正文直接分支；以后提供时仍须保留来源关系。若用户本意是首版支持，请推翻此补全。
- **需用户决定：** 否（推导）；用户可推翻。

| U1 | 已完成的回答是否也提供“重新生成” | A 只对失败／停止／中断提供重试；B 已完成回答也可重新生成 | A（首版更小、保存规则相同，以后加 B 不改数据） | 会话界面详细设计定稿前 |

## 5. 结论：可以有条件进入详细设计

**条件：**

1. 用户审阅并接受（或推翻）v2 中四项 A 类补全：MW-C01 重试另存新消息、MW-C02 引用清单与摘要归属、MW-C03 状态归属、MW-C04 首版不从总结直接分支。它们是推导而非新范围，但涉及对原文的解释，须用户认可后再写回现行文档。
2. 持久化详细设计从 v2 架构 §4.1–4.2 的实体与引用清单出发，先定稿；生成、总结、网络的设计引用它，而不是各自再定义引用关系。
3. U1–U3 在对应模块定稿前答复；未答复时不阻止其他模块。

**依据：** 产品范围、首版边界、D1–D8 口径在需求、架构与讨论记录之间一致；四工程依赖方向与课程职责映射清楚；版本、删除、归档、布局保存、迁移的事务规则已到可设计粒度；本次发现的缺口都能从已有决定推导出唯一的数据规则，未发现需要重开产品讨论的冲突。

**剩余风险：**

- 来源锚点依赖 LiveMarkdown 公共 API 的块级 SourceSpan，仅在 macOS 小样中验证；Windows、长文、库升级后的行为未知（MW-C13、MW-C23、MW-C26）。
- 真实 Chat Completions 只验证过短文本；多轮长文、压缩质量和取消计费均未验证。
- SQLite 备份、迁移、单实例和故障恢复尚无任何正式实现或临时库验证。
- 课程计数口径与 Root 等价性仍需老师确认（既有 MW-10）。
- 产品价值（延迟回顾是否真的更省力）完全未验证；进入详细设计不改变这一点。

**通往最终修订版的路径：** 用户确认 §5 条件 1 与 U1–U3 → 将 v2 的相关段落写回项目根目录现行文档（由用户授权的后续任务执行，本次不改原文）→ 按 [详细设计交接](detailed-design-handoff.md) 的模块顺序开展详细设计。本次只产出 v2，未产出 v3（见 [变更记录](change-log.md) 第 2 轮说明）。

### 答复引出的问题

#### MW-C29 重试与重新生成可作用于哪条回答（B 类，形成 U4）

- **位置：** v3 需求 §6.2；架构 §4.1。
- **场景：** 会话为 Q1→A1→Q2→A2。用户对 A1 点“重新生成”得到 A1′。按“每个提问取最新尝试”，续聊历史变成 Q1→A1′→Q2→A2，但 Q2 是针对 A1 提出的，A2 也基于 A1；模型看到的上下文前后矛盾，总结覆盖范围也无法说明 A2 基于哪一版。
- **影响：** 上下文与总结失去依据；U1 把重新生成扩展到已完成回答后，这种情况会经常出现（之前只有失败的回答，通常就是最后一条）。
- **处理：** v3 建议重试与重新生成只限会话最后一条回答；想沿较早回答换个方向，可以从原文创建分支。列为 U4。
- **阶段：** 会话与生成详细设计。**需用户决定：U4**（不阻断启动）。

#### MW-C30 短正文的阅读进度阈值（B 类）

- **位置：** v3 需求 §7.1；架构 §8。
- **场景：** 一篇总结只有五六行，打开时整篇已在视口内，进度立即是 100%，于是“打开即已读”，与 U2 明确的“仅打开不算”冲突。
- **影响：** 短总结的已读状态失去意义。
- **处理：** v3 建议对一屏可显示的正文另加停留时间或等效条件；阈值与时长是实现参数，不需要用户先定。
- **阶段：** 总结详细设计；实现时调参。**需用户决定：否。**

#### MW-C12 更新

U3 之后，新节点位置在计算后直接保存，只写该节点自己的一行，不顺带提交用户尚未保存的整理结果。剩下一个设计问题：放置新节点时参照内存布局还是已保存布局。参照内存布局时，用户随后对整理选“不保存”，新节点会留在被放弃的布局旁边；参照已保存布局时，新节点在画面上可能离来源较远。v3 交给网络详细设计决定，并要求说明两种情况的效果。放置算法结果应确定的建议保留，用于直接保存失败后重新计算。
