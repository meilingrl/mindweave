# Accessibility, UX robustness and i18n readiness — grade B

Accessibility has clearly been worked on deliberately and is far above course-project level: nearly every icon-only control has an AutomationProperties name, state is usually carried by words as well as colour, a single themed keyboard focus ring exists, custom widgets (workspace switcher, usage chart, segmented pickers) have keyboard handling and tests, and UI strings are centralised with only one stray literal. It falls short of an A because of structural gaps that a keyboard or screen-reader user will hit in the main flows: the in-window "dialogs" are not modal for the keyboard (no focus containment, three of them never take focus), the product's signature action (branch from a selected passage) has no designed keyboard path, several light-theme text colours that carry real content fail WCAG AA when computed from Colors.axaml, provider error details are reachable only by mouse hover, and no OS reduced-motion / high-contrast preference is read. i18n is single-language by construction (const strings, hard-coded Chinese date patterns) - acceptable since requirements do not ask for localisation, but number formatting mixes cultures. All of this was judged from source only; nothing was run with a real screen reader.

**Strengths**

- Screen-reader naming is systematic, not incidental: 115+ AutomationProperties usages across 21 view files; icon-only buttons pair ToolTip.Tip with AutomationProperties.Name (e.g. ShellView.axaml:42-43, 69-70, 197-198), sidebar rows expose checked state in the name ('title, 已选' via AutomationName, ShellView.axaml:113) and marker meaning via HelpText; the custom workspace switcher implements IExpandCollapseProvider (Views/WorkspaceSwitcherButton.cs:30-41) after a review found the expanded state was lost.
- State is rarely colour-only: unread/read/candidate badges are words (NetworkHomeView.axaml:84-97, 165-176), notices carry '!'/'?'/'i'/'✓' glyphs, selected nav rows add SemiBold weight plus background (Controls.axaml:53-56), the network legend uses shape and dash pattern plus text (NetworkHomeView.axaml:141-148), matching requirements §'不只靠颜色'.
- A single keyboard-only focus ring replaces Fluent's default on every button level, drawn 3 px outside filled buttons so it does not vanish into the accent fill (Controls.axaml:302-315); computed contrast of FocusRing is 4.4:1 (light) / 7.2:1 (dark) on the window, matching the comments in Colors.axaml:136 and :270.
- Keyboard paths were designed and tested for the custom widgets: workspace menu (Enter/Space/Down/Alt+Down, Home/End, wrap, Esc; SidebarHeader.axaml.cs:105-212), Shift+F10 row menu that defers to the platform gesture to avoid double-open (ShellView.axaml.cs:101-116), inline rename with focus return to the row (ShellView.axaml.cs:119-137), usage chart Left/Right/Home/End (UsageChart.cs:140-163), segmented pickers with TabNavigation=Once.
- String discipline is very good: a grep for CJK literals outside UiText*.cs in src/Mindweave.Desktop finds exactly one (ComposerView.axaml:35); everything else goes through UiText, and date/duration formatting is centralised in UiText.Formatting.cs with explicit cultures rather than implicit ToString().
- Dark theme text contrast is solid when computed from Colors.axaml: PrimaryText 14.4:1, MutedText 4.8-6.1:1 on every surface it is used on, Error/Warning/Link 7.5-9.4:1, badges 5.9-7.7:1. Contrast is also asserted in tests (SourceHighlightThemeTests, ConversationPolishTests, BranchMarksTests) and design notes record ratios (s7-ui-polish.md).
- Motion is restrained by design: 120-200 ms, at most 10 px, opacity/translate only, no layout per frame, disappearing is instant, one non-looping 600 ms badge pulse (Views/Motion.cs:45-62, Styles/Sidebar.axaml badge animation), and the spinner stops when off-screen or minimised (ActivitySpinner.cs:66-69).
- Toasts do not steal focus, are announced politely (ShellView.axaml:250-251) and pause their timeout under the pointer; small-window behaviour is handled by capping the sidebar so the page keeps 480 px (ShellView.axaml.cs:14-15, 249-258) with Window MinWidth/MinHeight 720x480.

**Not examined**

- Nothing was run: no real VoiceOver/Narrator/NVDA session, no real-window keyboard walk, no build or tests (read-only audit). Whether Avalonia 12.1.4 actually raises live-region events for the five AutomationProperties.LiveSetting usages was not verified.
- IME behaviour of the composer: ComposerView.axaml.cs:14-15 handles Enter in a tunnelling KeyDown handler and assumes 'Text composition (IME) consumes its own Enter first'. I could not verify this on macOS/Windows with a Chinese pinyin IME (headless tests cannot); if the assumption is wrong, committing a composition with Enter would send the message. Worth one manual check on each OS.
- LiveMarkdown.Avalonia internals (MarkdownTextBlock focus/keyboard/automation behaviour) were only inferred from symbol names in the DLL, not decompiled.
- SummaryView, StorageDetailsView, WorkspacesView, SettingsHomeView, OnboardingView, RecoveryView and StartupView were only skimmed via grep (automation names, key handlers), not read line by line; SidebarHeader.axaml.cs keyboard code was read only in grep excerpts.
- Windows high-contrast mode, Windows text-size scaling, and per-monitor DPI behaviour were not examined beyond confirming no code reads PlatformSettings colour/contrast preferences.
- Usage chart colour contrast (output series 1.9:1 / 2.4:1) is already recorded in TRACK.md '待决定' and was not re-reported.
- Sidebar splitter having no keyboard resize is a recorded deviation in docs/design/s7-ui-polish.md and was not re-reported.
- Right-to-left layout, non-CJK font fallback, and very long single-token names (no break opportunities) were not tested.

### a11y-i18n-1. In-window dialogs are not modal for the keyboard: no focus containment, and three of them never take focus

- Final: **high** (confirmed (one verifier lowered it)); auditor said high
- Where: `src/Mindweave.Desktop/Views/MainWindow.axaml:101`; effort M

**Evidence.** All prompts are Borders with class dialog-scrim stacked over the page inside one Panel (MainWindow.axaml:12-17, 25, 61, 101, 111, 116, 130, 149, 176). The scrim only blocks the pointer; nothing disables or removes the page underneath from tab navigation (no IsEnabled binding on PageLayers, no KeyboardNavigation.TabNavigation=Cycle/Contained on any dialog - grep finds TabNavigation only in Settings/Statistics segmented pickers). MainWindow.axaml.cs moves focus on open only for WorkspaceDeletion (line 133), ConversationDeletion (line 124) and the two backup dialogs (lines 108, 112). ExitTaskPrompt (line 101), ExitFailedPrompt (line 116) and LayoutPromptDialog (line 130) get no focus at all, and ExitCancel/ExitRetry/LayoutCancel have IsDefault but no IsCancel, so Esc does nothing there. The only Tab test near a dialog (BackupRestoreUiTests.cs:381-393) checks focus-on-open and Esc, not containment.

**Failure scenario.** (1) Keyboard user presses Cmd/Ctrl+Q while an answer is streaming with the caret in the composer: the 'stop and quit?' prompt appears but focus stays in the composer behind the scrim. ### a11y-i18n-2. Creating a branch from a selected passage - the product's core gesture - has no designed keyboard path

- Final: **medium** (confirmed in part); auditor said high
- Where: `src/Mindweave.Desktop/Views/Conversations/AnswerView.axaml.cs:63`; effort M

**Evidence.** The only entry to branch creation is BranchButton, created in code (lines 63-76) and shown in the window's OverlayLayer only while SourceAnchors.HasSelection is true (lines 351-376). Selection is produced by LiveMarkdown's MarkdownTextBlock (a SelectableTextBlock subclass per the package's symbols), which has no caret and no Shift+Arrow selection; the view only reacts to PointerReleased/KeyUp (lines 53-54). ### a11y-i18n-4. Network canvas is a focusable tab stop with no key handling, no focus visual and no automation peer; node dragging and edges exist only for the pointer

- Final: **medium** (confirmed in part); auditor said medium; already known in TRACK.md
- Where: `src/Mindweave.Desktop/Views/Pages/NetworkCanvas.cs:82`; effort M

**Evidence.** `Focusable = true;` (line 82) on a custom Control that overrides only pointer handlers (OnPointerPressed/Moved/Released/Wheel, lines 448-633); there is no OnKeyDown, no FocusAdorner and no OnCreateAutomationPeer. Decision D-018 (docs/design/decisions.md:77, s5-network.md:49) deliberately routes keyboard and screen-reader users to the list view, but the list (NetworkHomeView.axaml:158-181) offers only name + badges + open: it exposes no edges/relations, no source path, no 'return to conversation', and no way to arrange nodes. Keyboard selection on the canvas is possible only indirectly via the Find box (NetworkHomeViewModel.cs:148).

**Failure scenario.** Tabbing through the network page lands on the canvas: nothing visible changes and arrow keys, Enter and +/- do nothing, so the user appears to have lost focus (WCAG 2.4.7/2.1.1). A screen-reader user hears an unnamed element. Layout editing (drag a node, then Save layout) cannot be done without a pointer. Requirements v0.13 add user-made summary links and recommended nodes on the network; if those are built as canvas gestures, the keyboard/screen-reader gap grows from 'decorative view' to 'missing functionality'.

**Recommendation.** Short term: either make the canvas non-tabbable (IsTabStop=false) with an AutomationProperties.Name/HelpText pointing to the list view, or give it minimal keys (arrows move selection to the nearest node, Enter opens, +/-/0 zoom/fit) and a focus ring. Before implementing v0.13 links, define their keyboard equivalent (e.g. link actions in the detail panel and list rows) and expose edges in the list view.

**Skeptic: partially confirmed, medium.** The core claim holds; I could not refute it. Several supporting details are overstated.

**Confirmed**
- `NetworkCanvas` sets `Focusable = true` and overrides only `Render`, `OnSizeChanged`, `OnDataContextChanged`, `OnDetachedFromVisualTree` and the pointer handlers. There is no `OnKeyDown`/`OnKeyUp`, no `OnCreateAutomationPeer`, and no `IsTabStop`, `FocusAdorner` or `AutomationProperties` on it in code or XAML.
- The XAML places it as a bare `<v:NetworkCanvas Name="Canvas" />`, and the code-behind has no key handling for it. The only page key bindings are Ctrl/Meta+S and Enter in the Find box.

### a11y-i18n-10. Number formatting mixes CurrentCulture and InvariantCulture inside the same sentences; localisation is structurally single-language

- Final: **low** (not verified); auditor said low
- Where: `src/Mindweave.Desktop/UiText.Statistics.cs:58`; effort S

**Evidence.** `RequestCount` uses `string.Format(CultureInfo.CurrentCulture, "{0:N0} 次", count)` (line 58; likewise lines 163, 252-253, 258 and UiText.Formatting.cs:10-11 for sizes), while `Tokens` uses `count.ToString("N0", CultureInfo.InvariantCulture)` (line 60), money uses Invariant N2 (line 173), percentages Invariant (line 170), and price entry is parsed Invariant-only with AllowDecimalPoint (Mindweave.Application/Statistics/UsagePrices.cs:53).
