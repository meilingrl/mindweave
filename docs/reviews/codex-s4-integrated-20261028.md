### I1 · P2 — First queued/running Summary has no user cancellation entry

**Location:** [ChatView.axaml:6](/Users/meilingluo/Developer/Projects/mindweave.worktrees/codex-steady/src/Mindweave.Desktop/Views/ChatView.axaml:6), [ChatViewModel.Summaries.cs:18](/Users/meilingluo/Developer/Projects/mindweave.worktrees/codex-steady/src/Mindweave.Desktop/ViewModels/ChatViewModel.Summaries.cs:18). Supporting call path: `ChatView.axaml:46`, `ChatViewModel.cs:28,39`, `SummaryViewModel.Operations.cs:134–139`, `SummaryView.axaml:51`.

**What and why:** The new chat entry exposes Generate only. Once a first Summary is accepted, Generate disables, while the existing Stop button remains enabled only for an active **Reply** and calls the Reply coordinator. The only Summary Stop control is inside a version-operation confirmation on an existing Summary node. A first Summary has no node before successful completion, so a user cannot cancel it while queued or running without closing the entire application and stopping other work. This directly misses requirements §9.2 (`requirements.md:249,251`: cancellable queue; cancel before changing destination/configuration), and leaves the Task 5 Stop API unconnected to the normal Task 7 entry. App-wide shutdown is not an individual queue cancellation control.

**Fix direction:** Expose an explicit Summary cancellation action on the owning conversation or a reachable application-owned task surface. Bind it to the task identity the user saw, including queued work; do not reinterpret the existing Reply Stop in a way that cancels unrelated work. Preserve page/workspace navigation semantics and include the command in close/drain ownership.

**Minimum RED:** Through compiled Chat controls and a real session/store, accept the first Summary while both physical slots are held, then cancel it from the user entry: no Summary HTTP start and no node/version. Separately stop a running first Summary while a later Reply is active: only Summary is canceled, no partial version, Reply continues. Repeat after navigating away/back so the control does not depend on the accepting page instance.

**Actual checked scope:** Chat command/property bindings, unchanged Reply-only Stop guard, Summary coordinator Stop API, Main/Root ownership and the existing detail stop-before-delete test. That existing test starts with a node and therefore does not cover this entry gap. Static conclusion; no new test executed.

### I2 · P2 — Summary failures/stops/interruption are not projected to the user

**Minimum RED:** Use the production session and compiled Chat view with controlled invalid JSON, `length`, credential and transport failures. After each Changed notification, assert a visible terminal reason, correct retry availability, and zero new saved versions. Include Stop and recovered Interrupted, plus navigation/workspace switching to check identity ownership. The invalid-first-response case alone is sufficient to expose the present omission.

### I3 · P2 — Detail metadata uses current-version coverage for a displayed candidate/history version

**Location:** [SummaryViewModel.cs:120](/Users/meilingluo/Developer/Projects/mindweave.worktrees/codex-steady/src/Mindweave.Desktop/ViewModels/SummaryViewModel.cs:120). Supporting source: `SummaryViewModel.cs:93–101,127–130`, `SqliteWorkspaceStore.SummaryVersions.cs:37–46`, `MainViewModel.Summaries.cs:39–47,53–62`.

**What and why:** Initial version loading computes later content against the **displayed version's** `Coverage.OwnHighWaterSequence`. Metadata refresh instead does `hasLaterContent |= node.HasLaterContent`; the store explicitly calculates that node marker using `state.Node.CurrentVersionId`. For V1 current covering the first exchange, add a second exchange and generate candidate V2 covering both. Open V2: initially there is no later content. Any Summary/Naming metadata event now imports V1's true marker and says “此后有新内容，未纳入本次总结” about V2, although V2 covers all messages. The OR keeps this false warning sticky. Node/list markers being current-version-specific is correct per requirements §7.1; copying that marker into another version's detail is the bug. It violates the version coverage presentation required by §6.4 and Task 7 (`s4-summary-plan.md:131`).

**Fix direction:** Refresh later-content metadata using the displayed immutable version's own high-water mark (or an explicitly version-specific store query), with the same load/version ownership checks after awaits. Preserve the existing body, editing session and read epoch. Keep list/node markers current-specific.

**Minimum RED:** Create V1, append terminal own messages, generate V2 candidate covering them, open V2 and assert no later-content notice. Call `RefreshMetadataAsync` or deliver an unrelated naming Changed event; the notice must remain false. Then append genuinely newer own content and assert true. Also assert body, selected candidate and read epoch are unchanged. The current `Background_candidate_metadata_refresh_does_not_replace_saved_body_read_epoch_or_dirty_editor` test (`SummaryDesktopTests.cs:413–428`) views current V1 and never checks this marker.

**Actual checked scope:** Both detail calculations, exact storage SQL binding and Summary/Naming/Reply notification entry paths, plus policy/storage tests distinguishing terminal own rows from ancestor growth. Static deterministic mismatch; no new test executed.

Do not turn it into a persisted/complete node, mark it read, expose partial stream output as complete, or resend AI. Preserve access across page/workspace changes and failed-close Return; clear it only after reconciliation no longer needs the retained result.
