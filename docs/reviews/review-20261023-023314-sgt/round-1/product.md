# 第一轮独立产品／交互审查

审查对象：`v1/initial-requirements.md`、`v1/architecture-discussion.md`，辅以项目 README 和两个原型 README。这里只评价产品规则与可观察行为，不评价工程是否已实现。

审查方式：离线静态阅读；没有运行应用、编译、测试或访问应用数据。原型 README 中的既有验证只作为带范围限制的历史证据，不是本轮重新验证。未读取其他审查者报告。

## 总体判断

分支探索的基本承诺已相当明确：来源锚点、持续阅读位置、普通访问历史是不同对象；会话树与总结网络也没有混成一套“知识掌握”模型。首版保留用户主动总结、真实来源边、稳定总结节点，推迟语义自动关联和推荐，方向成立。

本轮没有发现可以直接定性的产品自相矛盾。开发前最值得补齐的是：总结遇到尚在变化的回答时的范围规则，以及候选版本在多次更新和手改交错时的操作对象。回顾网络在没有任何已总结祖先时还缺一个可观察的来源入口规则。以下风险不能当成已经发生的缺陷，也不代表用户已经批准相应修订。

## P-01：总结遇到进行中的回答时，冻结什么、何时重新提示遗漏尚不明确

- **位置：** 需求 §5.4、§7、§9；架构 §12、§15，特别是“生成开始时固定消息范围”和“后续消息提示后续内容未纳入”。
- **具体触发反例：** 一条长回答正在流式增长，用户点击“总结当前会话”；总结请求进入队列后开始执行，此时回答只收到前半段。之后原回答在同一个消息中追加了关键限制或纠错，但没有新增消息。若冻结只指消息集合，最终总结可能使用了不完整文本，界面又因没有“后续消息”而不提示遗漏。另一种实现若等执行时再读取全文，则用户点击时看到的范围和实际总结范围不同。
- **用户影响：** 日后回顾时把半条回答的总结当成完整解释；“后续内容未纳入”的提示无法可靠解释总结是否新鲜，也容易把未完成回答的确定语气带入总结。
- **依据可信度：** **合理风险。** 文档明确限制了分支只能从已完成／已停止回答创建，却没有为总结说明相应规则；“固定消息范围”也没有显式说明是否固定每条消息的文本长度／状态。不能据此断言实现必然只存消息 ID。
- **优先级：** **开发前明确。** 这是用户能否相信总结覆盖范围的规则，不宜只由数据库字段偶然决定。
- **最小修订：** 首版采用最简单的一条规则即可，例如当前会话存在增长中的回答时，暂不能启动总结，说明“等待完成或停止后总结”；已停止的部分回答允许纳入，但保留其不完整状态。若希望支持边生成边总结，则必须明确冻结文本快照及截至位置，并把同一消息后来追加的文字也视为未纳入内容。另需明确冻结发生在点击还是实际开始执行，界面与版本记录一致。
- **是否需用户决定：** **需要。** 是否允许边生成边总结是体验取舍；上述禁用方案只是审查建议，不是已确认决定。
- **最低成本验证与通过标准：** 用纸面时序列出“回答增长→点击总结→排队→开始→原回答继续追加／停止”两例。每个时点都应能唯一回答：当前按钮能否操作、总结包括哪段文字、完成后显示何种遗漏提示；不能把后来追加的文字暗示为已总结。此验证可先通过规则走查完成，无需新原型。

## P-02：多个候选与手动版本交错时，采用操作的对象和待处理数量没有封口

- **位置：** 需求 §4.2、§5.4、§6；架构 §12 的后台生成、§15 的候选／手动版本流程。
- **具体触发反例：** 当前采用版本为 V1；用户生成候选 C1 后没有处理，继续聊天又生成 C2；随后打开 C1 阅读，并在另一页面把当前版本手改为 V2。此时点击 C1 页面上的“采用”，必须清楚是采用正在看的 C1，而不是后台刚完成的“最新候选”C2；还必须知道 V2 是否仍能取回，以及 C2 是否继续待处理。现有“再次生成形成候选”“简单历史”允许多种结果，但没有限定其中一种。
- **用户影响：** 当前版本、待处理候选与用户手改相互穿插后，用户可能采用错版本，或不得不反复清理大量候选。即使历史保留而没有物理丢失，找回自己刚修改的内容仍会增加整理负担。
- **依据可信度：** **合理风险。** 文档已经正确要求不静默覆盖手写修改，且已读按版本独立；问题是这些保护在多候选、异步完成时如何落到用户的一次明确操作。没有证据说明现有原型实现过候选功能。
- **优先级：** **开发前明确。** 不必设计完整版本管理器，但需要一个可复述的最小规则。
- **最小修订：** 写明同时允许几个待处理候选、再次生成如何处理旧候选，以及采用／丢弃只作用于正在查看的那个稳定版本。无论采用何种数量策略，后台完成不得切换用户正在阅读的版本；当前手动版本应继续保留在简单历史中。不要仅用“最新候选”这种随时间改变的指针作为用户确认对象。
- **是否需用户决定：** **部分需要。** 候选数量和清理负担是产品取舍，需要用户选定或批准修订；操作绑定正在查看的版本、后台不替换阅读正文是既有不覆盖原则的直接细化，可先写成建议规则供批准。
- **最低成本验证与通过标准：** 用 V1、C1、C2、V2 四张卡走查上述次序，再交换两个生成任务的完成顺序。每一步都能唯一指出当前采用版本、正在看的版本、未读状态及待处理候选；采用 C1 后 V2 可从历史找回，C2 的状态明确。若选择只保留一个候选，也需展示旧候选去向，不能静默丢弃用户已在阅读的版本。

## P-03：未总结根及连续未总结祖先下的总结，仍需有无需猜测的来源入口

- **位置：** 需求 §4.1–4.2、§5.5、§6、§8.2；架构 §16–17。
- **具体触发反例：** “火车历史”根会话 R 没有总结；它的两个分支 A、B 各自有总结，A 与 B 之间没有直接来源关系。另一个根 R2 也有类似两个总结。按“只展示已保存总结”且只在“最近的已总结祖先与后代”间连接时，这四个节点均没有可连接的已总结祖先。用户隔三天只记得自己从“火车历史”岔开过两条路；若图上只有四个独立点，无法判断哪些属于同一个探索起点，也无法直接查看 R→未总结中间会话→A 的路径。
- **用户影响：** 最有价值的末端解释已经保存，但没有总结整条路径的用户反而难以恢复原问题；为让网络可用而被迫给根和所有中间会话补总结，会违背不要求额外整理的目标。
- **依据可信度：** **合理风险。** “多根探索群组”“按来源根主题组织”已经给出正确方向，因此不是已证实矛盾。缺口是：没有已总结祖先时，群组依据如何可见，以及从孤立节点能否查看完整来源路径；已有“经 N 个未总结会话”的边无法覆盖这个反例。
- **优先级：** **开发前明确行为，实施中验证呈现。** 无需现在选具体线型或布局算法。
- **最小修订：** 明确每个总结都能查看从根到来源会话的完整真实路径，并能打开其中未总结的会话；没有已总结祖先也不例外。多个总结共享未总结根时，用根会话标题等轻量群组信息识别同一起点；这些是来源说明，不制造空白总结节点，也不把兄弟节点连成父子。
- **是否需用户决定：** **通常不需要新增范围决定。** 这是已有“按来源根组织、完整路径可达、不伪造总结”的补全。若要新增一种可交互的非总结节点，则需要另行决定，不建议以此作为最小修订。
- **最低成本验证与通过标准：** 画一个含两个未总结根、连续两层未总结中间会话、四个已总结末端的静态草图。仅凭节点元信息和来源路径入口，审阅者应能识别四个节点的实际根，并打开任一中间会话；不要求补总结、不出现虚构直接父子关系、不要求用户先手工整理群组。

## P-04：首版手动布局的收益仍是假设，应允许它退出首个价值验证门槛

- **位置：** 需求 §1、§6、§8、§10；架构 §17 的可拖动节点和布局持久化。
- **具体触发反例：** 一个工作区只有 8–12 个总结，用户本来只想找到“三天前对四冲程的解释”，却先拖节点改善重叠，再调整缩放才能读标题。若拖动调整只是弥补初始布局，而不能比标题查找更快找到内容，用户得到了一项新的整理工作。未来自动增加节点时还要理解哪些位置属于自己的手动调整。
- **用户影响：** 可能把“留下记录”的简单流程扩成持续打理画布；首版投入了布局手工修正及其持久化，却尚未证明它帮助回顾。
- **依据可信度：** **待验证假设。** 现有原型没有网络，不能断言拖动有害或没有价值；稳定自动布局和视口恢复本身仍直接服务用户目标。
- **优先级：** **可推迟；不作为阻断缺陷。** 本条是首版删繁建议，不要求推翻已经确认的网络路线。
- **最小修订：** 若需要压缩首版，优先把手动拖动及其额外位置管理从首次价值验证门槛移出，保留稳定自动布局、标题查找、显示全部、打开总结及来源追溯。若保留拖动，应明确用户不需要拖动也能完成标准回顾任务，避免把“可手调”当作自动布局可用性的替代证明。
- **是否需用户决定：** **需要。** 拖动已在确认范围内；只能提出范围修订，不能由审查者自行删除或声称用户同意。
- **最低成本验证与通过标准：** 用同一组真实标题制作静态网络与可搜索列表／树的纸面样例，完成“找具体解释、找原问题、回到来源”三类任务，记录需要的定位与整理操作。若没有手动拖动也能完成且用户不主动提出位置整理需求，可先推迟拖动；若必须靠拖动才能辨认节点，应先修自动布局／标题可读性。此处不声称已完成比较，也不设置无依据的秒数门槛。

## 保留成立的结论

1. **分支来源与持续阅读位置分开。** 返回来源定位选区，已有入口重入和普通切换恢复目标阅读位置；保留草稿。它直接对应“岔开又回来”，无需另造复杂书签系统。
2. **普通后退与返回来源分开。** 架构 §11 已明确前者依据访问历史、后者依据真实分支关系。重启是否恢复完整后退栈仍列待确认，文档没有把未回答的问题冒称用户同意。
3. **只从已完成或已停止回答创建新分支。** 这避免对增长中 Markdown 的选区作过强承诺，同时不妨碍从旧回答分支。两个原型各有不同能力边界，未被混称为完整正式产品。
4. **总结稳定身份与版本分离。** 一次会话不因多次总结变成一堆网络节点；候选不自动覆盖当前手写内容。已读只是版本正文被打开，不代表掌握，采用状态也不等于已读。
5. **第一版只做真实来源关系。** 先保留回顾价值，再考虑语义关联、推荐、跨主题网络、多会话联合总结，能减少用户纠错及关系管理负担。
6. **多根工作区有合理用途。** 同一大主题可由不同问题开始，不必强迫用户把所有提问塞到一个根会话；本轮风险集中在来源群组可理解性，而不是多根概念本身。

## 已考虑但不列为缺陷的疑点

- **“已读必须等读完才标记”。** 驳回。现有定义是打开版本正文，且明确不代表掌握；精细阅读被有意推迟。若用户后来认为标记误导，可以再修术语，但本轮不以命名偏好推翻明确规则。
- **“从总结返回聊天应跳到某条原文”。** 驳回其作为现存矛盾的说法。架构 §16 已明确回到来源会话恢复其阅读位置，需要查看分支入口时另走来源语义；总结覆盖多条消息，不能无依据要求它总跳到一个固定句子。
- **“没有总结的会话必须在图里变成空节点”。** 驳回。没有总结不等于没有价值，但可以通过群组元信息和完整来源路径访问，P-03 不要求制造假成果或第二套会话图。
- **“首版不做删除／归档就是缺陷”。** 不成立为本轮阻断项。长期积累会产生管理负担，但安全删除被明确推迟；本轮没有真实长期使用数据支持扩大首版。后续试用若出现明显列表拥挤，再单独评估最小隐藏／归档，而不是顺势加入级联删除、搬迁或关系修复。
- **“必须先做复杂差异比较，候选才安全”。** 驳回。明确操作对象、保留历史和避免后台替换正文，已能形成首版可解释的保护；不应把完整版本编辑器作为解决 P-02 的默认代价。
- **“网络首版就应自动关联内容”。** 驳回。相关性与真实探索来源是不同信息，语义关联会增加纠正负担；没有证据表明它是当前回顾流程必需条件。

## 建议的本轮处置

先补 P-01、P-02 的行为选项和 P-03 的无已总结祖先场景，不扩展功能面。P-04 留作明确标注的删繁建议，由用户后续决定是否修订已确认范围。正式开发前不需要重新打开已解决的技术路线讨论，也不需要把两份原型重新运行一遍来回答这些产品规则问题。
