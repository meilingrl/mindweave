#### S1-F1 / P2：保存标题完成后，把等待期间的新编辑误标为已保存，随后刷新会覆盖输入

- **位置：** `src/Mindweave.Desktop/ViewModels/ChatViewModel.cs:40–45`，尤其第 43 行；关联 `:129–132`、`src/Mindweave.Desktop/Views/ChatView.axaml:5–6` 与 `MainViewModel.cs:254,259–265`。
- **触发：** 当前标题为旧值，用户输入 A 并点击保存。`RenameConversationAsync(..., TitleText)` 已捕获 A，但 SQLite 写入尚未完成；标题输入的 `CanEdit` 不包含 Rename 的执行状态，用户可以继续输入 B。写入完成后，第 43 行将 `storedTitle` 设成此刻的 B，而数据库保存的是 A。下一次 `RefreshTitle(A)` 看到 `TitleText == storedTitle`，便把 B 覆盖成 A。
- **影响：** 用户等待保存期间的新标题输入无提示丢失。协调器每 250ms 的 flush 即使无脏任务也会 Notify，Main 随后读取并刷新标题，因此不需要另一个自动标题任务才能触发覆盖。现有标题测试只检查静止的未保存编辑与一次完成的改名，没有覆盖等待中的再次输入。
- **修复：** 捕获本次提交的标题／编辑修订，将完成结果只应用到对应提交基线；后续编辑应保持 dirty。也可以在整个改名操作期间冻结标题编辑并通知绑定，但仍需处理已经排队的编辑通知。不要在 `await` 后用实时输入值代表已提交值。
- **针对性回归：** 在真实 SQLite 外包一层可控 Rename 写入屏障，开始保存 A，在屏障期间输入 B，完成保存并触发 Main 的标题刷新；断言 B 不被覆盖，再明确保存 B 后验证数据库为 B。若选择冻结策略，同时验证真实 XAML 的禁用状态与排队输入通知。

#### S1-F2 / P2：桌面发现核心保存失败后，生成调度器仍会开始新的请求

- **位置：** `src/Mindweave.Desktop/ViewModels/MainViewModel.cs:266`；关联 `ChatViewModel.cs:66–70`、`MainViewModel.cs:167–177` 及 `src/Mindweave.Application/Chat/GenerationCoordinator.Scheduling.cs:13,88–90,109–131`。
- **触发：** 已有回答 A 运行时，当前会话的后续草稿保存失败。Desktop 调用 `MarkPersistenceFailure()`，仅设置 `localPersistenceFailure` 并禁用 UI；它没有把失败通知协调器。若 generation 表仍可写（例如草稿写入单次故障或草稿表专属失败），A 完成后协调器的 `persistenceFailure` 仍为 false，既会调度已排队回答，也会接受并发送首条成功回答对应的新自动标题。无需用户点击新发送按钮。
- **影响：** 界面已经显示“保存失败，新操作已暂停”，但仍可能发起新的收费生成，违反 S1 Global Constraints 及架构 §12.1 的核心保存失败暂停新 AI 请求约定。特别是自动标题为失败发生后新接受的任务，不能用“已有排队请求已获接受”解释。现有 Desktop 故障测试检查 UI `CanSend`／新会话阻断；协调器测试只覆盖它自己发现的 generation 写入失败，未覆盖这条跨层通路。
- **修复：** 将核心保存失败的暂停状态提升为协调器可观察的应用级 gate，或由 Desktop 显式报告／解除外部持久化暂停。暂停应覆盖接受、排队调度和自动标题接受，并在外部草稿与协调器脏状态都显式修复成功后解除；已在运行的流仍可按现行规则保留／保存内容，不用取消任务冒充暂停。普通页面状态失败可以按现行降级规则另行处理。
- **针对性回归：** 使用当前 SQLite／受控 transport 夹具，只让草稿保存失败，在 Main 已显示暂停后结束 A；断言未增加标题请求且排队回答未开始。恢复草稿故障但尚未点击重试时仍不得外呼；显式重试保存成功后才按原优先级恢复一次。再检查退出失败后返回不会借此复活已停止任务。

### Minor — 明确保留的边界问题

- **本轮裁定：维持 Minor / P3，可延期，不作为这次 S1 正常路径的阻断项。** 当前协调器从零逐事件增加修订，且请求有两分钟超时；正常请求不可能实际达到该值。触发需要极端存储 API 输入、未来调用方或异常数据，并非普通聊天流程。此项未修复、未丢弃，也不因此前任务 Approved 而视为已关闭。
- 建议在存储层为终态保留修订空间，或定义不破坏终态不可变性的饱和终态迁移；之后补一个公共 API 回归，验证极值任务不会阻止同库其他活动任务恢复。仅拒绝未来最大值写入还需说明已有这种记录的处理方式。
