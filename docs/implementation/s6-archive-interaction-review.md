# S6 归档与恢复交互方案 · 待确认

这是稳健轨的详细交互提案，不是已实施或已批准的行为。已有依据为[需求 §8.2](../requirements.md)、[架构 §9.2](../architecture.md)；架构明确写道：“归档会话能否直接生成总结、恢复深层子分支时其已归档祖先如何显示，由详细设计提出方案并在交互评审中确认”。本次只确认这两项，其余已接受边界继续遵守。

## 一、从归档来源生成总结

**建议：允许显式生成总结，来源继续归档。**

1. 用户从网络总结回到归档来源，可以阅读原会话，页面显示“已归档”。
2. “总结当前会话”仍可显式使用，沿用已有范围、候选、费用说明和保存规则；完成后来源仍归档，网络总结照常保留。
3. 继续提问或创建分支时，先显示“恢复并继续”；仅阅读和总结不触发恢复。

另一可行方案是：归档来源的总结按钮也先要求恢复。这样所有新生成都集中在恢复后的会话中，但单纯整理归档材料也会改变归档状态。

两种方案均不自动生成、不改变模型或费用授权、不改写来源；未完成用户任务仍按既定规则先处理。

## 二、恢复深层分支后的祖先显示

例子：A已归档，子分支B在A归档前就独立归档；C位于B下，仅因祖先而隐藏。用户从C的总结回到来源，选择“恢复并继续”。

**建议：正常侧栏显示只读祖先路径行。**

```text
A 〔已归档 · 路径〕
└─ B 〔已归档 · 路径〕
   └─ C 〔已恢复，可继续〕
```

- A、B保持归档标记；路径行用于定位，点击仍是归档阅读。
- C及其分支内未独立归档的内容恢复可用；其他独立归档节点和其他分支保持原状态。
- C继续提问／建分支可正常进行；会话不搬迁，原父子来源、总结和阅读位置不变。
- 确认面板说明“恢复C所在分支；A、B保持归档，仅显示来源路径”。再次归档A仍是整体分支操作，按新范围重新说明。

另一可行显示是：在侧栏单列“已恢复分支”分组，将C显示为其中条目，并在旁标完整来源路径A→B→C；A、B仍归档，实际父子关系不改。它更紧凑，但侧栏层级与完整来源树分开呈现。

## 不涉及本次取舍的边界

归档默认隐藏、保留正文与网络总结；恢复父分支不会自动恢复此前独立归档的子分支。无依赖删除仍需检查子分支、总结、冻结引用与用户任务，且没有隐式级联删除。导出只取明确选择的已保存总结版本，不修改当前指针。这些不是本次重新征求确认的事项。

确认后将据此细化存储／导航方案与验收；在收到答复前，不实施依赖这两项选择的归档行为。
