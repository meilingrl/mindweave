# S2 分支与返回（连同 E1）

验收依据：需求 §11 前四行——从选句创建分支并继续追问；逐层返回来源；再次进入与普通切换各自恢复位置；关闭重开后消息、来源、阅读位置和草稿可恢复。需求 §6.2、§6.3，架构 §3.3、§3.4、§4.1、§4.2、§5、§6。演进接缝 E1 随本阶段落地；E2–E4、E6 已在迁移 v3 落地，名称见 [演进接缝](evolution-seams.md)。

## 数据（迁移 v4）

| 表 | 内容 | 引用 |
| --- | --- | --- |
| `branch_source` | 主键为子会话；父会话、来源消息、来源块序号；引用文字；锚点 JSON、锚点格式版本、渲染配置身份；创建时间 | 三个引用均 `RESTRICT`（跨实体） |
| `branch_context_range` | 主键 `(子会话, 祖先会话)`；`depth`（根为 0，按此排序，无需递归）；`max_seq` 为该祖先允许使用的最大消息序号 | 子会话 `CASCADE`（纯从属行），祖先 `RESTRICT` |
| `reading_position` | 主键 `(会话, 槽位键)`；视口顶部的消息、块序号、适配层细节 JSON 与格式版本；更新时间 | 会话与消息 `CASCADE`（纯从属行） |
| `draft` | 主键 `(会话, 槽位键)`；输入框文字；更新时间 | 会话 `CASCADE` |

分支父关系只存在 `branch_source`，`conversation` 表不加父列（架构 §4.1“不重复维护第二份事实”）。父会话里的分支入口由 `branch_source` 按来源消息推导。

## 创建分支（一个写事务）

在事务内检查，任一不满足即拒绝且不留任何行：

- 来源消息属于指定父会话，是回答，状态已终态（完成、停止、失败、中断；取消的回答没有正文），正文非空。被后来重试取代的旧尝试同样可以分支（需求 §6.2“旧尝试的正文及从它创建的分支入口保留可读”）。
- 引用文字非空、不超过 4,000 字；锚点 JSON 不超过 64 KB。
- 子会话与父会话同工作区（子会话直接取父会话的工作区，不接受外部传入）。

插入：子会话（无标题）、来源记录、祖先范围——复制父会话的全部范围行（depth 不变），再加 `(父会话, depth = 父链长度, max_seq = 来源消息 seq)`。父会话无范围行时即为根。来源是本会话自身、环或悬空引用都不可能出现：子会话是新 ID，范围只复制已存在的祖先。

## 上下文组装

`BranchContext.Assemble`（Core，纯函数）：

1. 按 depth 从根到父，对每个祖先取 `seq ≤ max_seq` 的消息，按 S1 规则“每个提问取最新可用尝试”选择。**例外：**每段范围的最后一条（`seq = max_seq`，即下一层分支的来源回答）即使是失败或中断的部分正文也保留——分支就是针对它的。
2. 然后是本会话自己的消息，同样按 S1 规则。
3. 链上每个分支会话（含当前会话）的第一个提问，在发送材料中前置“关于上文中的这段内容：> 引用”。存储中的提问不变。

来源回答之后被重试替换不影响已有分支：范围按 seq 冻结，新尝试的 seq 更大，不在范围内。任务的 `input_message_ids` 记录实际使用的全部消息 ID（含祖先）。预算与压缩在 S3。

## 锚点与渲染（Desktop 适配层）

- 回答用 LiveMarkdown.Avalonia 2.5.1 渲染，配置身份 `livemarkdown-2.5.1/default-pipeline`。提问仍为纯文本。
- 锚点沿用组件小样已验证的格式 1：每段记录源文区块范围、同范围序号、显示文字哈希、块内显示位置与引用；外加正文前缀长度与哈希；仅当源块与显示文字完全相同时记录精确原文起点。恢复先全部校验再改变选区，任一不符即拒绝。锚点相对于来源消息的某个文本块（E2 的块序号，首版恒为 0）。
- **降级（MW-C13）：**锚点无法恢复时，仍凭消息 ID 滚动到来源消息，显示保存的引用文字并提示“无法精确定位原句”；不在消息内搜索相同文字。
- 只有已终态、正文已保存的回答能发起分支；生成中的回答不显示“创建分支”。
- **生成中的选区（2026-11-06）：**生成中的回答可以拖选、复制。2026-10-27 记下的“生成中拖选位置不对”（目标 `[2,4)`，实际 `[0,4)`）经复查与生成中无关：那个测试在回答结束后又在同一点按下，两次按下在双击时间内，被算作双击（`ClickCount = 2`），双击选中整段连续中文，拖动以它的起点为锚，于是得到 `[0,4)`；中间隔开双击时间就正确。生成中拖选、拖选中途到达新文字、选中后继续到达文字（同段与新段）都正确，见 `StreamingSelectionTests`。
- **回答结束时保留选区：**真正的问题是选区在回答结束时丢失——页面用存储后的新行替换生成中的行，回答视图从增量构建换成全文解析，新控件没有选区。分支锚点不能用来搬运它：最后一块的源文范围和显示文字在结束前后都变了。处理：旧视图离开时，把选区按“块的源文起点、同起点序号、块内位置、所选文字”交给会话页；新视图取回后在同一位置核对文字一致才选中，任一部分不符就不选（例如结束时补上的 `**` 让后面文字的显示位置变化），不猜。恢复后的选区和其他已完成回答一样可以创建分支。旧视图离开时键盘焦点随之丢失，而复制快捷键只送到有焦点的回答，所以原来有焦点时，新视图在没有别的控件取得焦点的前提下取回焦点，选区仍可用快捷键复制。拖选进行中回答结束时，保留结束前已选的部分，剩下的拖动不再改变选区。

## E1 视图槽位

- 工作区运行期状态分两层：`WorkspaceRuntime`（工作区）→ `ViewerSlot`（槽位）。当前主区、各主区内容栈属于槽位。首版每个工作区只有一个槽位，键为 `primary`。
- 阅读位置与草稿以 `(会话, 槽位键)` 为主键；页面创建时得到所在槽位的键。
- 导航请求可携带目标槽位，缺省为发起请求的槽位；首版只有 `primary`。“返回来源”在当前槽位中打开。

## 返回、再次进入与普通切换

| 操作 | 导航意图 | 结果 |
| --- | --- | --- |
| 子会话页“返回来源” | `ReturnToSource` | 在当前槽位的探索栈压入父会话页，定位并高亮来源；失败按降级处理。后退回到子会话 |
| 父会话里点分支入口 | `Open` | 打开子会话，恢复它自己的阅读位置；不新建分支或书签 |
| 侧栏切换 | `Open` | 恢复目标会话自己的阅读位置，不跳到来源 |

“返回来源”只依据分支关系，不依赖后退历史。子会话页顶部显示祖先路径（各祖先标题，可点击打开）与引用文字。侧栏按分支层级缩进显示：根会话按最近更新排序，子会话按创建顺序排在父会话之下；未命名的分支以引用文字作为显示名。

## 阅读位置与草稿

- **持有者：**`ReadingStateService`（Application）在内存保存每个 `(会话, 槽位)` 的最新值，页面读取以内存为准，因此离开后立刻重新打开也不会读到落后的数据库值；落盘按键防抖 500 ms，退出时在关闭数据库前全部写完。
- **阅读位置：**阅读线（视口顶部下方 8 px）所在的消息 ID、块序号，以及适配层细节：源文区块范围、同范围序号、字符位置和阅读线距该字符顶部的距离（D-010）；提问只记消息顶部偏移。滚动停止约 200 ms 后采集。恢复时按“同一源块的同一字符 → 同一消息的同一偏移 → 会话末尾”逐级降级（需求 §6.3 允许回到对应段落）。打开时若有“返回来源”的定位请求，以定位为准，且只生效一次：之后经“后退”回到该页时恢复阅读位置。
- **草稿：**会话页输入框内容随输入更新到服务；发送成功清空并删除行。新会话页的草稿只保留在页面实例中（会话尚不存在）。

## 性能（E6）

`PerfSeed` 加入十层分支链，基准“为最深分支组装上下文”预算 300 ms（完整规模）。

### 超长回答的渲染（2026-11-06）

**方法：**`tests/Mindweave.Desktop.Tests/Performance/AnswerRenderPerformanceTests.cs`。无界面窗口（1000×700），但用真实 Skia 排版；正文由确定性生成的中文 Markdown 组成，每节含标题、粗体、无序与有序列表、引用、代码块，每三节一张表格，取约 3 万字与 10 万字（分别 851 与 2,829 个文本块）。完整规模由 `scripts/perf.sh` 运行（`MINDWEAVE_PERF=1`，Release，约 20 秒）；常规测试只跑 3 千字的冒烟版，验证各条测量路径可用，不检查耗时。每项先预热，测量前回收垃圾，取中位数。

- **显示已完成的回答：**只测回答视图——设置数据（解析＋建控件），首次排版，首帧绘制。
- **打开会话：**从侧栏打开存有该回答的会话，到页面定位完成并排版（含存储读取、页面与视图创建）。
- **生成中每次更新：**分两层。渲染器层按 LiveMarkdown 的增量步骤逐步计时：全文解析（应用里在后台线程），以增量更新应用（只更新源文范围变化的块），再排版。整个应用层用假服务在已有长回答的末尾每次推送 40 字，统计界面线程直到页面显示并排好这段文字所做的全部工作（节流刷新、视图模型、回答视图、LiveMarkdown、页面排版与跟随滚动），不含后台线程。

**结果**（本机 macOS，三次运行的范围）：

| 项目 | 3 万字 | 10 万字 | 预算 |
| --- | --- | --- | --- |
| 显示：解析＋建控件 | 52–55 ms | 187–195 ms | — |
| 显示：首次排版 | 87–94 ms | 260–267 ms | — |
| 显示：合计 | 139–152 ms | 444–476 ms | 400／1,000 ms |
| 显示：首帧绘制 | 23–25 ms | 47–51 ms | 不设 |
| 从侧栏打开 | 189–204 ms | 577–624 ms | 500／1,500 ms |
| 每次更新：后台解析 | 约 2 ms | 3–10 ms | 50 ms |
| 每次更新：渲染器应用＋排版（界面线程） | 约 1.5 ms | 2–5 ms | 16 ms |
| 每次更新：整个应用的界面线程工作 | 6–6.5 ms | 10–13 ms | 25 ms |

**结论：**

- 没有“每段都重绘”的二次方代价。LiveMarkdown 每次更新都重新解析全文，代价随长度线性增长，但在后台线程，10 万字时仍远低于 50 ms 的刷新间隔（解析慢于刷新时多次更新会合并，不会排队）；界面线程只更新最后一块，渲染器层的代价只略有增加（1 万字约 1.5 ms，10 万字 2–5 ms）。整个应用层随长度略增（10 万字约 10 ms），按每 50 ms 刷新一次约占界面线程 20%，未改。
- 打开 10 万字的回答约 0.6 秒，主要是一次建出 2,829 个文本块并全部排版：文本块不虚拟化，锚点与阅读位置也依赖全部块已排版。属线性代价，未改。若以后需要更快，方向是按视口分批建块，但要同时改锚点与阅读位置的前提。
- 预算约为本机测量值的 2–2.5 倍，只对本机有意义；Windows 上桌面测试整体约慢 3.5 倍，这组基准未在 Windows 上跑。
